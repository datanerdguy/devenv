# 0015. Dados: Podman, clientes na máquina e bibliotecas por projeto

Data: 2026-11-24 · Status: aceita

## Contexto

Engenharia de dados e MLOps pedem containers (bancos, serviços, compose), ferramentas para olhar dados e notebooks.
A máquina é modesta (GPU MX110 de 2 GB, 7,6 GB de RAM), e o devenv quer tudo leve.

## Decisão

- **Podman, não Docker.** Sem serviço ligado o tempo todo e sem root. `podman-docker` faz o `docker` chamar o
  `podman`, e o `podman.socket` do usuário (ligado pelo chezmoi, acorda sob demanda) atende quem espera o socket do
  Docker, pelo `DOCKER_HOST`. Docker só se um projeto exigir de verdade.
- **Bancos em container, por projeto** (`compose.yaml`); na máquina, só os clientes: `psql` e harlequin.
- **No terminal:** duckdb, visidata e harlequin (pelo uv: no AUR ele puxa muitas dependências Python).
- **Python por projeto**, com o uv. Notebooks: marimo nos projetos novos, Jupyter quando o projeto já usa.
  Modelo em `templates/python-data/`.
- **Sem LLM local** (ollama) nesta máquina: só modelos pequenos e lentos caberiam.
- **Nuvem e MLOps** (aws, kubectl, terraform...) entram pelo `mise use` de cada projeto, quando houver.

## Consequências

- Nada de serviço de container rodando à toa, e nada de grupo `docker` com poder de root.
- Ferramenta que fala com o socket do Docker funciona pelo `DOCKER_HOST`; uma que procure só `/var/run/docker.sock`
  precisa do caminho do Podman na config dela.
